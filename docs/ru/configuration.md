# Настройка

[English](../configuration.md)

Перед изменением маршрутов или инструментов посмотрите итоговую конфигурацию через CLI:

```sh
agentgate config path         # путь к пользовательскому файлу
agentgate config show         # результат слияния всех слоёв
agentgate config validate     # проверить конфигурацию без запуска модели
agentgate config profiles     # доступные профили маршрутизации
agentgate config extensions   # расширения и источники правил ревью
agentgate modes               # маршруты в виде таблицы
```

Проверка валидирует структуру настроек и ссылки. Она не выполняет вход, не запрашивает доступ к моделям и
не доказывает, что установленный CLI поддерживает каждую настроенную модель и уровень усилия.

## Порядок слоёв и файлы

Настройки читаются в таком порядке; последующие значения переопределяют предыдущие:

| Порядок | Источник |
|---|---|
| 1 | Встроенный [config.json](../../internal/assets/config.json) |
| 2 | Профиль маршрутизации из ключа `profile` пользовательского файла |
| 3 | Пользовательские `extensions/*.json`, по имени файла |
| 4 | Пользовательский `config.json` |
| 5 | `.agentgate/extensions/*.json` репозитория, по имени файла |
| 6 | Проектный `.agentgate.json` |
| 7 | Личный `.agentgate/config.json` текущего checkout |

Пользовательский каталог — `$XDG_CONFIG_HOME/agentgate` или `~/.config/agentgate`, если переменная не задана.
Проектные пути отсчитываются от рабочего каталога checkout. Старые имена `.claude-dev` и
`.claude-dev.json` продолжают читаться, если соответствующие им `.agentgate` отсутствуют.

Объекты сливаются по ключам. Списки в расширениях **дополняются уникальными элементами**, а в обычных
конфигах **заменяются целиком**. Например, личный список `worktree.copy` или `instructions` правила ревью
задаёт полный нужный набор, а не дополнение. Значение `null` в явном слое удаляет ключ из результата;
результат всё равно должен пройти проверку. Сам файл должен быть JSON-объектом, а не `null` или массивом.

`accounts` принимается только из пользовательского конфига. Профили, расширения, проектные и личные
настройки checkout не могут переопределить список подписок. Так репозиторий не выбирает оплачивающие его
работу аккаунты. Это не превращает проектные скрипты и MCP-инструменты в песочницу для недоверенного кода:
подключайте их в репозиториях, код которых намерены запускать.

## Изменение и проверка

```sh
agentgate config init                         # создать начальный файл, только если его ещё нет
agentgate config set max_parallel 3
agentgate config set modes.medium.backend opus:high
agentgate config set modes.medium.scout '""'   # пустой маршрут явно отключает разведчика
agentgate config unset modes.medium.backend  # удалить пользовательское переопределение
agentgate config validate
```

`config set` принимает ключ через точки и по возможности разбирает значение как JSON, иначе — как строку.
JSON-объекты и массивы нужно заключать в кавычки оболочки. `set` и `unset` меняют только пользовательский
файл. Более поздний проектный или личный слой всё ещё может определять итог, показанный в `config show`.

Каждая правка через CLI проверяет и пользовательскую конфигурацию отдельно, и её слияние для текущего
checkout. Только после успеха файл атомарно заменяется под блокировкой. Отклонённая правка оставляет
конфигурационный файл неизменным, а одновременные CLI-правки не теряют независимые ключи друг друга.
После ручного изменения файла запускайте `config validate`.

Проверка отклоняет неизвестные поля и неверные типы итоговой конфигурации, неподдерживаемые версии схемы,
ссылки на неизвестные модели, ошибочные маршруты и имена профилей, повторы или ссылку на себя в списке
замен, неверные роли и оси, отрицательные лимиты и таймауты. Обязательные значения вроде `max_parallel` и
`worker_memory_mib` должны быть положительными. Поддерживаемая версия схемы — `1`. Нечитаемый личный
профиль вызывает ошибку, а не молча заменяется встроенным профилем с тем же именем.

`config unset` открывает значение из нижележащего слоя; это не обязательно встроенное значение.
Аналогично, `config profile default` удаляет только выбор профиля и сохраняет другие пользовательские и
проектные настройки.

## Профили и псевдонимы моделей

Профиль маршрутизации лежит под пользовательскими переопределениями. В комплект входит альтернатива `codex`:

```sh
agentgate config profile codex
agentgate modes
agentgate config profile default
```

Профиль Codex направляет всех воркеров через CLI Codex. Он не устанавливает этот CLI и не меняет хуки лида;
для установки есть [команды setup](cli.md). Явные переопределения маршрутов сохраняются и могут конфликтовать
с новым профилем. Посмотрите их через `config show` и уберите устаревшие перед переключением.

Личные профили хранятся в `profiles/<имя>.json` рядом с пользовательским конфигом. Имя состоит из строчных
латинских букв, цифр, `_` и `-` и начинается с буквы или цифры; пути и пробелы запрещены. В профиле допустимы
описание `about` и обычные ключи конфигурации. Личный файл с именем встроенного профиля имеет приоритет.

Запись модели содержит три поля:

| Поле | Значение |
|---|---|
| Ключ объекта, например `opus` | Псевдоним маршрута; строчные латинские буквы, цифры, `_` и `-` |
| `provider` | `claude` или `codex`, выбирает CLI-адаптер |
| `model` | Точный идентификатор, передаваемый этому CLI |
| `pool` | Непустая метка для отображения и группировки; не создаёт квоту и не подменяет показания провайдера |

Идентификаторы из комплекта находятся в [config.json](../../internal/assets/config.json) и
[профиле Codex](../../internal/assets/profiles/codex.json). Это изменяемые значения по умолчанию, а не
обещание доступа с любого аккаунта. Замените пример идентификатора ниже на модель, поддерживаемую вашим CLI
и аккаунтом:

```sh
agentgate config set models.custom '{"provider":"codex","model":"your-enabled-model-id","pool":"codex"}'
agentgate config set modes.light.backend custom:medium
```

При работе с одним провайдером каждый активный маршрут и каждая замена должны вести к его моделям.
Если включено модельное ревью, оставьте модель ревьюера, которая не писала ни одну часть реализации этой
задачи. Два псевдонима одной модели независимости не создают. В профиле Codex такие маршруты уже заданы;
для работы только через Claude можно создать личный профиль. Точная политика независимости и значения
по умолчанию описаны в [маршрутизации моделей](model-selection.md).

## Маршруты и ревью

Маршрут — это `<псевдоним>:<усилие>`. Допустимые значения усилия: `low`, `medium`, `high`, `xhigh` и `max`;
адаптер передаёт выбранное значение CLI провайдера. Успешная проверка структуры не доказывает, что конкретная
модель поддерживает этот уровень усилия.

| Ключ | Для чего |
|---|---|
| `modes.<режим>.scout` | Сбор контекста; пустая строка отключает разведчика |
| `modes.<режим>.escalate_to` | Верхняя граница усилия для поддерживаемого повышения у писателя |
| `modes.<режим>.architecture` | Архитектурные маршруты; `critique: true` требует ровно два |
| `modes.<режим>.backend`, `.frontend` | Писатели по домену потока |
| `modes.<режим>.review` | Полосы вида `{"axes":["correctness"],"route":"astra:high"}` |
| `modes.<режим>.blocking` | Блокирующие уровни из `P0`, `P1`, `P2`, `P3` |
| `modes.<режим>.critique` | Перекрёстная критика двух архитектурных маршрутов |
| `modes.<режим>.architecture_timeout_s`, `.writer_timeout_s`, `.reviewer_timeout_s` | Ограничения процесса в секундах; `0` означает значение среды выполнения; план может переопределить лимиты писателя и ревьюера |
| `ui_designer`, `visual_reviewer`, `consultant` | Маршруты локального UI-дизайна, необязательной браузерной проверки и консультаций |

Режимы: `light`, `medium`, `heavy`, `ultra`. Оси ревью: `correctness`, `architecture`, `simplicity`,
`security`, `design`. Локальные `review_rules` добавляют инструкции приёмки без выдачи новых инструментов;
см. [расширения](extensions.md).

`reviewers_excluded` перечисляет псевдонимы, которым запрещено ревью. По умолчанию исключён `sol` — это
политика маршрутизации, а не утверждение о результатах бенчмарков. Во время выполнения дополнительно
исключается каждая фактическая модель, писавшая часть задачи: включая фронтенд, частично неудачную работу,
заменивших писателей и предыдущие этапы. Правило действует и на запасных ревьюеров. Если независимых
маршрутов не осталось, ревью явно завершается ошибкой; валидация конфига не может предсказать все будущие
сочетания авторов и замен.

## Замены моделей

```json
{"fallbacks":{"fable":["astra","opus"],"astra":["fable","opus"],"sol":["sonnet"]}}
```

Пример переопределяет три списка, сохраняя остальные ключи замен из нижних слоёв. Список задаёт настроенные
псевдонимы в порядке повторных попыток. В нём не допускаются собственный псевдоним или повторяющиеся элементы.

После распознанного отказа по квоте сначала пробуются другие пригодные аккаунты той же модели, затем —
объявленные псевдонимы с тем же усилием. Аккаунты с уже известной нехваткой квоты пропускаются. Кандидат в
ревьюеры также пропускается, если писал реализацию или исключён из ревью. Замены записываются в результат
задачи. Ошибки входа, конфигурации, протокола и обычные сбои выполнения не приводят к переключению модели.

Продолжаемая сессия провайдера сохраняет модель; запасные модельные маршруты для такого продолжения не
используются. Смена аккаунта внутри провайдера всё ещё может быть предпринята; если продолжить сессию
нельзя, возвращается явная ошибка. Ротация, оплата и работа с учётными данными описаны в [аккаунтах](accounts.md).

## MCP-инструменты воркеров

Воркеры получают только MCP-серверы, явно назначенные через `worker_mcp`, а при включённой визуальной
проверке — ещё и браузерный инструмент этой задачи. Адаптер не загружает обычную конфигурацию MCP и плагины
CLI лида. Запись сервера использует такие ключи:

| Ключ | Поведение |
|---|---|
| `command`, `args`, `env` | Запуск stdio-сервера внутри песочницы воркера, в checkout; `command` не может быть пустым |
| `tools` | Список разрешённых инструментов; отсутствие или пустой список означает **все инструменты сервера** в обоих CLI |
| `roles` | `scout`, `architect`, `writer`, `reviewer`, `consultant`, `designer`; отсутствие или пустой список означает только `scout` |
| `hint` | Краткие инструкции в задании воркера |
| `refresh` | Необязательная команда в формате argv перед первым использованием сервера в операции |
| `refresh_timeout_s` | Лимит обновления; по умолчанию `300`, `0` выбирает это значение, отрицательные числа запрещены |
| `writable` | Существующие реальные подкаталоги checkout, доступные воркеру на запись даже в роли только для чтения |

`writable` действует на весь процесс воркера, а не только на один MCP-инструмент. Ограничивайте его
каталогом кэша. Абсолютные пути, корень checkout `.`, `.git`, выход наружу и символические ссылки в пути
отклоняются; отсутствующие каталоги не создаются и не выдаются на запись. Подготовьте кэш подходящей
командой setup или refresh до использования.

Сам сервер запускается внутри песочницы воркера, но **`refresh` — снаружи**, как проектный скрипт.
Параллельные вызовы одной операции ждут общее обновление. Если оно завершается ошибкой, необязательный
сервер не подключается, а воркер получает указание читать исходники, не доверяя устаревшему индексу.
В heavy и ultra по умолчанию нет разведчика, поэтому сервер только с ролью `scout` не попадёт к их архитекторам.

Не храните секреты в общих расширениях. Унаследованные `FIGMA_ACCESS_TOKEN` и путь к приватному профилю
браузера удаляются из окружения воркера; он получает экспортированные файлы дизайна. Вывод конфигурации
может содержать значения, явно записанные в `worker_mcp.env`, поэтому проверяйте его перед передачей.
Полные примеры и настройка правил ревью находятся в [расширениях](extensions.md).

## Прочие настройки

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `max_parallel` | `4` | Верхняя граница процессов воркеров, если в запросе нет `-N` |
| `worker_memory_mib` | `512` | Бюджет памяти на воркера для ограничения параллелизма; лимиты cgroup учитываются |
| `retention_days` | `14` | Хранение старого завершённого состояния; `0` отключает очистку; активные и ещё не перенесённые изолированные задачи сохраняются |
| `worktree` | `{"default":false,"copy":[],"setup":[],"setup_timeout_s":1800}` | Изоляция и подготовка нового worktree; см. [изоляцию](isolation.md) |
| `staging` | `{"max_files":25,"max_streams":5,"isolate":"auto"}` | Пороги этапов и политика изоляции; `0` убирает соответствующий порог; см. [этапы](stages.md) |
| `plans_home` | не задан | Общее хранилище планов, выбранное через `agentgate plan link <папка>` |
| `accounts` | пусто | Управляемые профили CLI; см. [аккаунты](accounts.md) |
| `design` | не задан | Каталог экранов дизайна и настройки локального стенда; см. [дизайн](design.md) |
| `playwright_mcp` | `~/.local/share/agentgate/playwright-mcp/node_modules/@playwright/mcp/cli.js` | Установленный входной файл браузерного MCP для необязательной визуальной проверки |

Браузерной проверке также нужны Node.js и работоспособный Chromium. Задайте `playwright_mcp`, если пакет
находится в другом месте, затем запустите `agentgate doctor`. Визуальная проверка валидирует объявленные
origin локального стенда и ограничивает ими браузерный MCP; это не обещание полной сетевой изоляции
процессов воркеров. Все адреса объявленных origin должны разрешаться в loopback. Процесс работы с дизайном
и браузером описан в [дизайне](design.md).
