# Brief — what real lead sessions showed, and what changes

**Status:** plan, nothing implemented. **Written:** 2026-11-16. **Versions analysed:** 0.16.0 and 0.16.1
(three Claude Code leads), 0.15.0 (one Codex lead).

## Why

0.16 moved the work of a task into `run`. The sessions that followed show where the time goes now: not into
writers, but into the lead working around the tool. In the longest session (one checkout, three tasks, about 28
hours of wall time, 73 operations) the lead made:

| What | Count |
|---|---|
| `amend` calls (11 revisions of one plan) | 18 |
| refused commands | 7 |
| look-ups in `guide`, `reference`, `help`, `modes`, `config` | 23 |
| `status` and `show` calls | 64 |
| commands that parsed the tool's output with `jq`, `python` or `sed` | 141 |
| direct reads of state files and design-kit sources | 18 |

Twice a limitation of the tool changed the user's product: a false "streams overlap" refusal moved GraphQL
documents to another directory, and a layout check that can only open a URL produced two new deep links and a
backend query. After one task reached `done`, CI failed twice on things the gate never ran.

The causes fall into six groups. Group A was confirmed by reading the code (A8 in part: the exporter's
behaviour was seen in a session, not read). Groups B–F are gaps the sessions show.

## Sources

- Claude Code transcripts: skinhole `9158130b` (light, three stages), skinhole `760a038a` (medium and heavy,
  Figma, isolated), polygon `7556fe3e` (a ready plan handed to `/dev`).
- Codex rollout `01a1da08` (0.15; kept for what it shows about dropping and deleting a task).
- Operation journals under `~/.local/state/agentgate/<project>/<session>/operations/`.

## Decisions taken

The user delegated the open decisions. They are settled as follows.

| Question | Decision |
|---|---|
| One `decide {work}` instead of `requirements`, `reassessment`, `brief`, `streams` | Yes. The four forms are removed, not aliased: a lead reads the protocol in every session and keeps no stored inputs. |
| Targeted operations in `amend` | Yes, beside the complete plan, which stays. |
| An unmet criterion goes to its writer without the lead | Yes, when the reviewer says code is missing; within the same limit of automatic rounds as findings. |
| The last stage runs every declared check | Yes. Receipts bound to unchanged inputs are reused, so the cost is the checks whose inputs changed. |
| `drop` and `forget` | Yes, both on the user's word only. |
| A reviewer in light mode by default | Yes: one lane, `astra:medium`. The lead reviews only when a configuration sets `review: []`. |
| Re-routing a started stream to another model | No. A stream keeps its session; the guide says so. A stream that must change hands is closed with `done: true` and replaced by a new one. |
| Queueing a command behind a running operation | No. The refusal names the running action and what is possible meanwhile (`tell`, `stop`). |
| New tests | One regression test per confirmed defect of group A, nothing broader; scenario tests for B1, B2, B5 and B6. No live runs on real models: the user does not want their quota spent. A model's behaviour seen in a session is reproduced by a scripted fixture, and each release has a dry run: the real binary, sandbox and git, with workers that replay recorded answers. |

## A. Defects

Each is fixed where it is; none changes the lead protocol.

**A1. A leading `/dev` hides the flags.** A request passed as `{"request": "/dev -m --grill …"}` came out in
ultra mode; the lead edited `plan.json` by hand twice. `ParseRequest` (`internal/dev/request.go`) stops at the
first token that is not a flag. *Change:* drop one leading `/dev`, `$dev`, `!dev` or `/$dev`; accept
`--plan`, `--review` and the other action words written as flags. *Done when* that request parses to medium
with `grill: force`.

**A2. Streams that cannot collide are refused.** `random/graphql/**` against `random/*`, then against
`random/+*`: "could name the same file". `overlap` (`internal/dev/scope.go`) treats any two patterns with nested
prefixes as overlapping unless their extensions differ. *Change:* decide the intersection of two patterns
exactly, segment by segment (`*` within a name, `**` across directories). *Done when* both pairs pass and
`a/**` against `a/b/*.ts` is still refused.

**A3. A pattern that names a directory does not own what is inside.** `migrations/*_streamer_giveaway` did not
cover `migration.sql`; the task stopped after twenty minutes of writing. A wildcard entry with a trailing slash
is not turned into `/**` either (`normalizeEntry`). *Change:* an entry that matches an ancestor directory of a
path owns the path; a wildcard entry ending in `/` gets `/**`. *Done when* the file is owned in both spellings.

**A4. A stall with no correction behind it.** After `decide {requirements: [{id, action: "fix"}]}` the task
answered `stall (unchanged-content)`; no writer had received the work. `demand` (`decide.go`) does not set
`Ruled`, and `progress` (`autopilot.go`) compares the content with the start of an older correction. *Change:*
`progress` judges only findings the last correction carried; an accepted finding outside it is new work.
*Done when* that sequence opens a correction.

**A5. Failing checks are not run again after the correction aimed at them.** With an unchanged tree `classify`
reads the receipts from before the correction and answers `stall (check-still-failing)`. Before that, checks
that failed because a database was stopped went to the writers. *Change:* a failing receipt older than the
last completed correction is outstanding, not failing. When checks that passed now fail and no file of the
task changed since, the lead gets the need with the end of the log; writers are not started. *Done when* a
check repaired outside the code passes on the next `run` without a writer.

**A6. A blocked stream stops every other stream.** `amend` added stream B with `A.after = [B]` while A was
blocked; `answer` woke A alone, `run` did nothing, B never started. In `Run` any blocked writer ends the write
step. *Change:* streams whose dependencies are complete run while others wait for an answer; `answer` runs the
unfinished dependencies of its stream first. *Done when* that plan completes without folding B into A.

**A7. The tool's own design packages are reported as foreign changes.** A plan `design.screen` given as a
bare name put about 200 files into the worktree root; the need `scope` followed, and the lead edited the
user's `.git/info/exclude`. *Change:* a `screen` that does not exist yet is placed under the screens directory
(`design.screens`, default `.agentgate/design`); that directory is excluded from the audit of foreign changes.
*Done when* an imported design leaves `git status` of the worktree clean.

**A8. A failed design import loses its reason.** The answer was "could not import the design; see the
exporter error above" with nothing above and no entry in `needs`. `prepareDesigns` keeps the last output line
and returns an error. *Change:* report the exporter's own line; make it a need `setup` that `status` shows. An
asset Figma does not render is recorded in the package manifest and skipped, not fatal. *Done when* the
session's node `8669:28386` imports with a warning.

**A9. Every layout failure is the lead's.** Three causes looked the same: a redirect to login, a root
attribute the writer spelled differently, a stale backend. `check.mjs` exits 2 for all of them and Go maps 2
to `setup`. *Change:* exit 3 when the requested page loaded and the root is missing — a failing check for the
writer, with the `data-*` attributes the page does carry; exit 2 for a page that did not open or ended at
another path, with that path in the message. The need leads with the tool's message, not its argv. *Done
when* the three causes give three different answers.

**A10. A requirement due at the last stage has no receipts of earlier stages.** The reviewer answered
`partial` twice ("earlier-stage summaries are not evidence"); the lead copied checks into the last stage in two
amendments. `checksFor` gives a stage its own checks and the plan's. *Change:* the last stage of a staged plan
runs every declared check. *Done when* such a requirement is verified without an amendment.

**A11. The commit message of `land {how: "commit"}`.** It was `dev: storage: Added a server-owned…`, cut
mid-word; the lead amended the commit. *Change:* `message` is required for `commit`; the guide says to follow
the repository's convention. *Done when* `commit` without it is refused with that sentence.

**A12. Two refusals that should not be.** Check evidence is accepted only by receipt id (`client:test` was
refused); `duplicate_of` with `decision: "accepted"` is refused. *Change:* a check is named by id or by a
unique part of its command, and the refusal lists the valid ones; an entry with `duplicate_of` is recorded as
a rejected duplicate whatever its decision says.

**A13. `show plan` returns the instructions of the last amendment.** `update`, `authorized` and `rework` are
fields of the plan; sending the plan back repeats the rework. *Change:* they belong to the revision record.
A state written earlier drops them on load.

## B. Actions that are missing

**B1. Give work to a writer.** `decide {brief}` did not reach the writer, `decide {requirements}` was refused
for lack of an assessment, `tell` is a note. `amend` with `rework` became the one way that works. *Change:*
`decide {work: [{stream, note, requirement?, escalate?}]}` opens a correction for those streams at any step
after writing. It replaces `requirements`, `reassessment`, `brief` and `streams`. A lead decides three things:
it rules on findings, it judges a patch where no reviewer does, it gives work.

**B2. Change one thing in the plan.** Today: `show plan`, a `jq` program over 50 KB, `amend`. *Change:*
`amend` also takes named operations — `scope` (files added to a stream), `checks` (added to or removed from a
stage), `requirements` (added, or moved to a stage), `timeouts`, `design` — each with `update`. Validation and
the rules for accepted stages are those of a complete plan.

**B3. Change the mode of a prepared plan.** The mode lives in a flag inside the request text; a `-m` given
before preparation cannot become `-h` without editing that text. *Change:* `mode` in the plan and in the input
of `prepare`, stronger than the flag. When a flag sets a mode below what the assessment gives, `because` says
so with the risks, and the lead tells the user.

**B4. Attach files.** A brief in `~/Downloads` and four reference screenshots could not be passed: the lead
inlined one and described the others in prose. *Change:* `prepare {attachments: [paths]}`, absolute paths
allowed; files are copied into the preparation, shown to the worker (images as images) and carried into the
task for writers and reviewers.

**B5. Fix the notes of a finished task.** "Fix what needs fixing" after `done` took a landing, a hand-written
plan and a second task. *Change:* the answer at `done` lists the notes in one line each; `decide {findings}`
on a finished, unlanded or in-place task reopens it with those findings accepted.

**B6. Drop and forget.** Asked to revert a task and remove it from history, a lead restored files by hand and
deleted the state of every repository on the machine. *Change:* `drop` for a task that worked in the checkout
restores the files the task changed to the tree it started from, and refuses for any file changed since by
someone else; `forget` removes the state and history of one finished or dropped task of this checkout.

**B7. Notes the reviewer raises again.** A later pass is not told its own earlier notes and reports them under
new ids (2 became 4, 3 became 6); the lead rejects duplicates by hand. *Change:* later passes receive
`open_notes`; a finding at the same path and line on the same axis joins the existing one. A requirement
result carries `cause`: `code`, `proof` or `plan`. `code` goes to the owning writer as findings do; `proof`
and `plan` go to the lead.

## C. What the lead cannot see

**C1. One shape of answer.** `route`, `show plan`, `check`, `tell` and `architecture` each answer differently,
and the lead guesses keys. *Change:* every command that touches a task answers with the common object, its own
data under `result`. The object gains `running {action, since}` and `last {action, state, error}`.

**C2. The Stop hook.** It says "run `agentgate status`" when the reason is a refusal that came back in a
second while the lead believed the command was running. *Change:* the hook's message carries the last refusal
and the kinds of `needs`.

**C3. Needs that say how.** A need names fields; the lead looks the shape up. *Change:* each need carries
`input`: the JSON to send, with the real ids, streams and valid references filled in. `what` begins with the
cause in the tool's own words. A refusal that depends on a value lists the valid ones.

**C4. A writer at work.** Asked "is the backend hanging?", the lead inspected file times and
`pg_stat_activity`. *Change:* `status` shows, per running worker, the elapsed time, the time since its last
event and that event in one line; the event stream already exists for `watch`.

**C5. Writer timeouts.** Twenty minutes ended a writer in the middle of work. *Change:* a writer is stopped
after ten minutes without an event; `writer_timeout_s` is a ceiling, 3600 by default.

**C6. The final receipt.** At `done` the lead searched JSON for the models that ran. *Change:* the answer at
`done` carries `receipt`: routes per role with substitutions, checks with results, notes left, rounds and
time per stage.

**C7. Volume.** A brief of 44–52 KB opens with the whole request; `status` repeats 2 KB of requirement text and
complete argv arrays. *Change:* the brief quotes the first lines of the request; needs clip `detail`; checks
are named by a short label. `show` has the rest.

**C8. Readable evidence.** The lead parsed `packet.json` and the architecture receipt (a report inside a JSON
string) by trial. *Change:* `show review` and `show architecture` print what a person judges and the input to
answer with.

**C9. Plan names.** `plan-https-www-figma-com` came from a Russian request. *Change:* the preparation worker
returns `name`; the fallback ignores flags, action words and URLs.

## D. Quality of the result

**D1. Checks that miss the change.** The plan named two test files; the test beside the changed file and the
client typecheck were never run, and CI failed on both. *Change:* the preparation prompt asks for the tests
that reference what the plan changes and for a typecheck of every project whose shared types change, as
authorizations where they are heavy. A test file a writer adds or changes that no declared check runs is
reported in the packet and in the answer.

**D2. Proof beyond the declared proof.** A reviewer kept a requirement `partial` because a check had not
exercised every branch; the lead built a third 4 GB database for a P2 clean-up. *Change:* the review prompt
says what verifies a `check` requirement — a current passing declared check that exercises the changed code —
and that a wish for more proof is a note.

## E. Figma and the stand

**E1. The catalogue.** Depth 3 is fixed in `prepare.go`; preparation stopped three times, and the lead called
the private `figma.mjs` about twenty times and pasted the output into `notes`. *Change:* a blocked preparation
may return `design_requests [{node, depth}]`; the tool reads them and continues the same session, up to three
rounds. `reference design` says how Figma is reached (`figma login`, `figma status`).

**E2. States that a URL does not reach.** Eight designs shared one URL and differed by `data-state`. *Change:*
a design entry takes `steps` (`click`, `fill`, `wait` on selectors) run before measuring, or
`compare: "review"` for a state judged from the picture. The preparation prompt requires one of them for every
entry that shares a URL with another.

**E3. The stand.** One command and fixed cookies. The page needed services, data and a session; the lead
spent two hours building them after the writer had finished. *Change:* `design.stand` takes `services`
(commands with their `ready` URLs) and `session` (a command that prints cookies). Before the writers of a
design stage start, the stand is started and every design URL is opened: a page that is not built yet is
fine, a redirect to another path or an unreachable stand is a need `setup` then, not an hour later.

## F. Orientation

The look-ups were for ten things: the shape of the lead's review, changing a mode, recording an architecture
decision, the plan and amendment fields, where configuration lives and how routes fall back, whether a stream
can change model, landing, how Figma is read, the input of `tell`, passing a file. C3 removes about half of
them. For the rest:

- **One source.** Pages under `internal/assets/skill/`, written by situation: "a need of kind X", "the writer
  asks for a file outside its scope", "change the mode", "set the models", "a Figma task", "the task is
  finished". Each holds the complete input.
- **Three more pages:** the answer of every command; where things are and what is never read or run directly
  (state, the design kit); refusal text → cause → what to do.
- **Installed as a skill** for both clients by `agentgate install`; `agentgate reference <page>` prints the
  same text, so nothing drifts.
- **`guide` shrinks** to the loop, the table of needs and the index of pages.

*Done when,* in the user's next working sessions of the same kind (read from their transcripts, not from test
runs): fewer than five look-ups, no parsing of output and no read of state.

## Not in this plan

- The sandbox, provider adapters, account routing and the panel: nothing in the sessions implicates them.
- Queueing commands, re-routing a started stream, patching the client's output trailer (`[exited with code
  N]`, which breaks `jq` on a background output file): C1 and C2 remove the need to parse that file.
- The repository-side stand of skinhole: E3 gives it a place in the configuration; writing it is that
  repository's work.
