# Brief — an interface nobody designed, and an environment nobody prepared

**Status:** accepted, not implemented; every decision is settled (see "Decisions taken"). **Written:** 2026-11-17.
**Version analysed:** 0.20.2 (one Claude Code lead, three tasks in one session).

## Why

One session, three tasks, 4.8 hours of tool time:

| Task | Mode | Tool time | Before the first writer |
|---|---|---|---|
| A: finish the streamer giveaway (backend, gateway E2E) | heavy | 71 min | 16 min |
| B: streamer access in the admin | `-l`, then medium | 99 min | 30 min |
| C: the interface of B, built again | medium | 117 min | 13 min |

Task C exists only because the interface of task B was unusable. Nobody in the pipeline asked how an operator
would use it; the user had to ask for a usability judgement himself, and the rework was a whole second task.
Separately, in five of six stages the first writer pass ended `BLOCKED`, never because of code.

## A. The interface nobody designed

**What happened, in order.**

1. The preparation worker (`astra:medium`, with `--grill`) first proposed a separate «Стримеры» section:
   account → page address → granted codes. That was streamer-first, and close to what was finally built.
2. Its four questions were about permission, shared codes, revocation and the page name. None was about use:
   what an operator comes to do, what he has in hand when he starts, how many codes he gives at once.
3. The user asked: «и почему плодим вообще отдельный пункт? мб внутри промокода как-то? нет?». The worker took
   the question as a decision, moved everything into a tab of the promo-code card, and wrote the prohibition
   into the stage acceptance: "No new route, menu item or global streamer directory is introduced". It named
   no cost and offered no middle option.
4. The architect (`opus:high`) accepted that, listed the global section under `alternatives` as "unrequested",
   and returned no questions.
5. The plan's `ui` was the local-change form: ten criteria about states, keyboard and copy. `visual` was null.
   The reviewer (`opus:high`) checked those criteria and found two P2 code defects.
6. The UI designer (`agentgate design`, `internal/assets/prompts/ui-design.md`) was never called. Its prompt
   already says "identify the user's primary job" and "check the flow for … dead ends and avoidable steps".
7. After the user insisted, a three-minute `consult` on `astra:medium` found five problems; the first was that
   a streamer can be reached only through some promo code. The revised design chose a button in the page
   header: no new route and no menu item, which answered the user's original objection as well.

**Causes.**

- `prepare.md` allows `BLOCKED` only for a "product, data, security or authorization decision" and describes
  `ui` as `{summary, criteria, preserve}` or `{skip}`. The form `{design, acceptance}` exists in the plan
  (`agentgate reference plan`) but the preparation worker is never told about it, so a new surface is planned
  as a local edit.
- `design` needs `task`, `brief` and `usage_context` written by the lead (`internal/dev/ui.go`), and the guide
  forbids the lead to design. The guide's steps name `architecture` only; `design` appears as "(Figma)".
- `architecture.md` speaks of boundaries, data, load and risks. It says nothing about the person who uses the
  result, and "no … without a concrete requirement" reads an entry point nobody demanded as speculation.
- `prepare.md`, "Whose words are whose": a note that quotes the user is the user's decision. A question is
  quoted the same way as an instruction.
- `review.md` has no axis for use; browser verification is "only when the user asked".

**A1. The preparation states the jobs.** When UI files are in scope and the change adds a surface — a screen,
a tab, a dialog flow, a new task for a person — the plan's `ui` carries `usage`: who uses it, the jobs they
come to do, what each job starts from (what the person already has in hand), how often, what is done in bulk.
Facts the code and the request do not give are questions to the user; "how the interface will be used" is a
valid reason for `BLOCKED`. *Done when* the request of task B yields either a question about the starting
point (from a streamer, from a code, both) or `usage` that lists "find a streamer without knowing a code" and
"give one streamer several codes".

**A2. The designer runs without the lead.** For a plan with `ui.usage`, `architecture --plan` also runs the
mode's `ui_designer` on the brief, `usage` and the UI files, and its `flows`, `rejected_alternatives` and
`open_questions` come back in the same answer: the questions beside the architect's, the receipt as
`ui {design, acceptance}`. No new command and no new role; `design` stays for a lead that has a specification
to revise. `start` refuses a plan with `ui.usage` and no accepted design. *Done when* task B's plan cannot
start before a designer has returned flows for every job.

**A3. Jobs are walked, in both prompts.** `ui-design.md` and `architecture.md`: for every job in `usage`, walk
it from its starting point to its end in the proposed interface; count the steps and name what the person
must already know. A job that cannot be done, or that goes through an object unrelated to it, is a risk with a
remedy or a question — never an alternative dismissed as "unrequested". Where a function lives and how a job is
entered is the user's decision when it changes how a job starts: ask it with options, a middle one included.

**A4. A question is not a decision.** `prepare.md` and the revision round of `architecture.md`: when the
user's words are a question or a doubt ("why X", "maybe Y?", "нет?"), answer it — what each option costs for
each job, with locations — and change the plan only where the answer holds. When the change would alter how a
job starts, return it as a question with the options and the recommended one. A prohibition is written into
the brief or the acceptance only from a statement, never from a question. *Done when* the user's sentence from
step 3 produces a comparison and a question, and no "No new route…" line.

**A5. The reviewer reads the jobs.** A stage that covers `ui.usage` adds the axis `usability` to its first
lane, the way `design` is added today (`internal/dev/review.go`): each job is traced through the written code.
Severity as in decision 2. This is the check the consult made in three minutes, moved before acceptance.

**A6. The browser is proposed.** For a plan with `ui.usage` the preparation writes one scenario per job into
`setup` as an authorization to ask for, with the stand it needs, as it already does for heavy checks.

## B. An environment nobody prepared

Blocked first passes: a database not created; a migration not applied; `ARCHIVER_TEST_BASE_URL` absent; a
stand not started; four packages missing from `node_modules` after the disk filled. `prepare` returned
`setup` as 8–13 paragraphs of free text mixing commands, authorizations, a stop condition ("CURRENT STOP: …")
and notes to the coordinator ("apply the user's requested medium mode"). `start` reads none of it.

**B1. Prerequisites are data.** `setup` becomes three lists: `authorizations` (what to ask the user, with what
it would catch), `prerequisites` (`{id, what, argv, stage, after}`: what must exist before a stage's writers
start, or after a named stream has written — a database from the migration that stream edits), and `notes`.
Before the writers of a stage start, unmet prerequisites are a need `setup` with their commands; one that
waits for a stream is raised when that stream ends, and the writer is told not to block on it. Text about the
process — when to stop, which mode — is refused in all three. *Done when* task A's stage 1 raises `setup` for
the two databases instead of a blocked writer.

**B2. The task's environment.** `start` and `amend` take `env_file` (decision 6): a private path whose
variables the tool gives to every declared check and never prints. In the session one call without the variable sent three
checks to another database, failed the measurement and blocked a writer for a round. *Done when* a check run
from a shell without the variable still reaches the task's database.

**B3. A stand started from the task's worktree.** `admin-service` rewrote
`generated/apps/admin-service/schema.graphql` on start; twice it became a need `scope` that the lead settled
with `git checkout` in the worktree. *Change:* a need `scope` for a path that matches `generated` and has no
writer behind it carries the `input` that restores it.

**B4. `doctor` and the browser.** "browser tooling ok" checks the Playwright MCP script only. Chromium was
absent: the pass failed after 43 seconds, and the user answered 39 minutes later. *Change:* `doctor` looks for
the browser binary; `run {visual}` checks it before anything else; a plan with scenarios names the install
command among `authorizations`.

**B5. Free space.** A full disk broke `yarn install` silently. *Change:* `doctor` and `start` warn below a
configured amount of free space.

## C. Work after `done`, and words said while the tool runs

**C1. A requirement said during an operation is lost.** `amend` was refused ("an operation is already
running"); `tell` reached the writer only; by the time the operation ended the task was `done`, and `amend`
was refused again. The reviewers never saw the requirement. *Change* (decision 4): `amend` that only adds
requirements or checks is validated, kept as pending, shown in `status`, and applied before the next review
starts; an operation that would end the task applies it first, so the task cannot reach `done` past it.

**C2. New work on a finished task.** 0.17 B5 reopens a task with accepted findings. A revised design or a new
requirement still needs a landing and a new task: here the architect revised the design (4 min), then a new
task prepared again (7.5 min) and designed again (5.5 min). *Change* (decision 5): on a finished, unlanded
task, `amend {architecture, requirements}` and `decide {work}` open a further stage on the same plan, context
pack and receipts. *Done when* the rework of task B runs as its stage 3.

**C3. A wrong refusal.** `architecture {revise}` on that task failed with "no task is open in this session:
name the saved plan in `plan`". The task was open and done. *Change:* say that, and what is possible.

## D. The cost before the first writer

Task B, asked for with `-l`: five `prepare` calls and four `architecture` calls before `start`.

**D1. Stopping after the design is not plan content.** The lead sent "stop after the architecture" to the
preparation worker; it went into the brief and `setup`; removing it took another `prepare` (163 s) and, since
the receipt is bound to the brief, another `architecture` (87 s). *Change:* the guide says that stopping
after the design is not calling `start`; `prepare.md` keeps process instructions out of the brief (B1).

**D2. A mode change is not a worker's job.** `prepare` continues the worker on every call
(`internal/dev/prepare.go` has no path that returns before it), so `{"mode": "medium"}` alone costs a worker
pass; the only way without a model is editing `plan.json` by hand and `plan save`. *Change:* a `prepare`
input that holds `mode` and nothing for the worker — no notes, answers or attachments — rewrites the saved
plan's mode and starts no model.

**D3. The answer of a revision.** `architecture {revise}` returned every earlier lane: 54 thousand characters
with the new design at the end. The lead began to cut answers with `grep` and `head`, which the guide forbids.
*Change:* the answer holds the present design, what changed and the questions; `show architecture` has the
history.

## E. Smaller

- **E1. `status` at a stage boundary** shows "0 of 10 checks" and nothing about the accepted stage; the lead
  read `git log` in the worktree. *Change:* accepted stages in one line each: checks, reviewers, findings.
- **E2. The Stop hook** fired three times while the lead was doing authorized preparation and once three
  seconds after `run` ended; each time the lead paused to quiet it. *Change:* with B1 most of these become a
  need `setup` the lead is visibly working on; the hook does not fire for a `setup` need that was raised in
  the last minutes.
- **E3. The guide contradicts itself:** "never read anything under `~/.local/state/agentgate`", while the
  task's worktree and the check logs that `show checks` names are there. *Change:* name the two exceptions.
- **E4. Language.** The lead answered in English three times after long English tool answers. *Change:* the
  reminder that accompanies a user's message says to answer in the user's language.
