# 0001 — What the 0.14 → 0.15 fixes and the run logs showed

Status: evidence for the records that follow. Collected 2026-11-14.

## The fixes

Eleven defects were corrected between 0.14.0 and 0.15.0. They look unrelated; nine of them have one of
three causes.

| Defect | Cause |
|---|---|
| `continue`, a repeated `launch` and `answer` bypassed a stale architecture | No single entry into a writer round: every command re-implemented its own guard |
| `replan` left an unfinished round "awaiting review": it could be neither continued nor reviewed | The phase was a string assigned in eight places; one assignment produced a combination nobody handled |
| A reviewed stage with a `partial` requirement could not finish, be fixed or be replanned | The same: no action was legal in a reachable state |
| `plan` accepted a staged request and the validator refused its stages | "Planning" and "implementing" were one field of the plan, so a proposal could not hold what it proposed |
| Files added by a generator after launch were taken as their own before-image | The before-image was a list of files captured at launch; a file discovered later had none |
| Stage and task baselines were confused when files were admitted late | The same |
| A prepared context was not reused by staged tasks | The scout's cache key included the stage brief and the repository digest, both of which change every stage |
| `covers` was read as "contributes to" and a foundation stage was held to end-to-end behaviour | The plan could not say "this stage works towards R3; R3 is due later" |
| Corrupt state of a neighbour session released its file claims | Reading state had two code paths |
| `config show` needed writable state | Unrelated |
| A browser fixture passed `--root` twice | Unrelated |

## The runs

Two staged backend tasks and one design task were driven by a Codex lead on the 0.14–0.15 binaries. The
numbers below come from the operation journals, the workers' event streams and the lead transcript of the
larger backend task (four stages, medium mode). Private names are omitted.

### Where the tokens went

| Consumer | Input tokens | Share of the task's work |
|---|---|---|
| The lead session | 22.2 M | 247 tool calls, of which **196 were polls** of a running command |
| Reviewers (12 lanes, both tasks) | 13.4 M | several lanes read 2–3.6 M each |
| Scout (11 runs) | 6.9 M | one per stage and per changed contract |
| Preparation (14 runs) | 4.6 M | each a fresh session that explored the repository again |
| **Writers (10 lanes)** | **4.9 M** | the only lanes that produced the change |

For every token spent writing code, about nine were spent around it. The largest consumer was not a worker
at all: it was the lead waiting.

- The lead polled every 1–10 seconds. The client allows an empty poll to wait **300 seconds**; nothing in
  the guide said so, and the guide's own advice ("about 30 seconds") was wrong for that client.
- Each poll was a full model turn over a context that averaged 90 k tokens and reached 160 k. The guide and
  the reference (19 k tokens together) were loaded three times.
- The most expensive reviewer read a 61 kB packet by parsing it with scripts, then 874 kB of diffs of which
  590 kB were generator output (migration operations, generated clients).
- The scout cost more than the writers it was meant to save from reading.

### Where the time went

| Operation | Count | Minutes | Not completed |
|---|---|---|---|
| `prepare` | 14 | 24.8 | 3 |
| `launch` | 4 + 10 | 10.7 + 63.0 | 1 + 5 |
| `review` | 4 + 11 | 7.3 + 15.9 | 0 |
| `replan` | 5 | 0 | 2 |

Twelve of the fourteen preparations ran before the first writer started, over 45 minutes:

- six were spent on plan-format errors, one error per run (a line-number citation in a file list, a
  directory in a file list, an underscore in a stage name, `kind: "check"`, missing streams, stages refused
  for a planning request). The validator reported the first error only, and the plan travelled as an untyped
  JSON string, so the provider's schema enforcement could not help;
- three returned `BLOCKED` for reasons that were not product decisions (it could not write a file it was
  never meant to write; discovery "was not finished");
- every answer from the user started a new worker that read the repository from the beginning.

### Dead ends

Every refused command in the journals was classified. The dominant class is "this command is not legal in
this phase":

| Refusal | Times |
|---|---|
| `launch` while reviewed / awaiting review / held / an unfinished gate exists | 8 |
| `replan` on a held task; `replan` of a staged task | 2 |
| `finish`: "this mode needs at least one declared check" — discovered after every stage was written | 1 |
| `check`: the command is not in the plan — the only way to add one was closed | 1 |

Two of these were terminal. One task waited ninety minutes for a new release of the tool. The other was
cancelled by the user after all four stages were written and reviewed, because no command could add the
check that `finish` demanded.

### What worked

- Independent review found real defects, and its `partial` verdict on the misassigned requirements was
  correct. The failure was that nothing could be done about a correct verdict.
- Continuing a writer's session for a correction and a reviewer's session for a recheck was cheap and held
  context.
- Checks before reviewers, content-bound receipts and file ownership between sessions never produced a false
  acceptance in the logs.

## What published work says

- **Writes should stay single-threaded; verification should be a separate agent with a clean context; the
  author should filter the reviewer's findings using its wider context.** Cognition, "Multi-Agents: What's
  Actually Working" (2026), reversing only part of its 2025 "Don't Build Multi-Agents": a generator–verifier
  loop works, parallel-writer swarms still do not.
- **Every harness component encodes an assumption about what the model cannot do, and the assumptions go
  stale.** Anthropic, "Harness design for long-running application development" (2026): with a stronger
  model the sprint decomposition and context resets were removed, the planner stayed load-bearing, and the
  evaluator "is worth the cost when the task sits beyond what the current model does reliably solo". The same
  post: models asked to judge their own work "confidently praise it"; a separate evaluator tuned to be
  sceptical is tractable. Evaluation there cost a few percent of the build; here it cost more than the build.
- **Coordination is the main cost of a multi-agent system, and an orchestrator that verifies before it
  aggregates is what contains error amplification.** "Towards a Science of Scaling Agent Systems" (2025):
  on SWE-bench Verified every multi-agent variant scored below a single agent; centralized coordination
  amplified errors 4.4×, independent agents 17.2×; token overhead was 58–515 %.
- **The most frequent multi-agent failures are step repetition, reasoning that does not match the action,
  not knowing the termination conditions and disobeying the task specification.** "Why Do Multi-Agent LLM
  Systems Fail?" (MAST, 2025). Fourteen preparations and a lead with no legal move are instances of the
  first and the third.
- **A plan is a living document: a change of course is recorded with its reason and the plan stays the one
  source a new session can restart from.** OpenAI ExecPlans; OpenSpec keeps the accepted specification
  stable and expresses a change as an explicit delta; GitHub Spec Kit validates the plan across artifacts
  before implementation rather than at its end.

## Conclusions the following records act on

1. The lifecycle needs one definition of what is legal, from which the guards, the advice to the lead and
   the tests are all derived (0002).
2. A plan needs one shape, and a requirement needs a due stage (0003).
3. "Before" must be answerable for any file at any time (0004).
4. The lead should be asked for decisions, not for keystrokes, and a reviewer's finding should be answered
   by the author before it reaches the lead (0005).
5. Changing the plan in the middle of the work is the ordinary case (0006).
6. Preparation is one conversation; a second explorer is not paid for (0007).
7. Waiting must be cheap and the protocol must fit in the lead's context (0008).
8. A reviewer reads one patch, not generator output (0009).
